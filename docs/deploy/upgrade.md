# 升级指南

> **首次安装的人不需要这一页**,直接看[安装指南](install.md)。这里讲的是「已经在用,想换到新版」。

系统采「向前相容迁移」:升级时**资料保留**,资料表结构的变更由 `api` 容器启动时自动执行(`alembic upgrade head`),你不需要手动改资料库。

> **开始前先备份。** 升级本身不会删资料,但任何重大操作前留一份备份是好习惯。到「系统管理 → 资料备份与还原 → 立即备份」,或见[备份指南](backup.md)。

## 升级到 v1.3.0:系统会自动先备份

v1.3.0 是第一个**改动资料表结构**的版本(新增单双周课程用的栏位)。升级本身已在 v1.2.0、v1.2.10、
v1.2.19 三个版本的实际资料上验证过:课表、配课、课时、请假、代课、统计、巡堂表升级前后完全相同。

为了让没看到这份说明的学校(例如 `.env` 设 `IMAGE_TAG=latest`)也受到保护,**v1.3.0 起,
`api` 容器发现资料库结构需要升级时,会先自动备份一次再升级**:

- 备份出现在「系统管理 → 资料备份与还原」,标示「**升级前自动备份**」,**不会**被每日备份的轮替删除。
- 升级后,系统管理员在「系统管理 → 系统版本」会看到一次提示,写著这份备份的档名。
- 自动备份万一失败(例如硬碟空间不足),系统**照常升级、可以正常使用**,提示会改成说明失败原因;
  这时请尽快按「立即备份」。要退回旧版仍有两条路:升级前一晚的每日自动备份,或下方的「退回指令」。

仍建议升级前自己按一次「立即备份」并把档案下载到另一台电脑保存——那是唯一不在同一台主机上的一份。

## 一条规则:`docker-compose.yml` 要跟著版本走

系统的容器组成会随版本演进(例如 v1.1 就多了一个 `worker-ops` 容器)。**升级时请连 `docker-compose.yml` 一起更新到新版**——方式 A 重新下载该档,方式 B 的 `git pull` 会自动带到。

沿用旧 compose 档而漏了新容器时,系统不会默默坏掉:相关功能会**立刻**回一句说得出处置的错误(例如「维运背景服务(worker-ops)没有在执行……请更新 docker-compose.yml」),补上新档案再 `docker compose up -d` 即恢复,资料不受影响。

## 方式 A:拉取映像部署(最常见)

在放 `docker-compose.yml` 的资料夹内:

```bash
# 1)(建议)先在系统内按「立即备份」

# 2) 更新 docker-compose.yml 到新版(容器组成可能有变动)
#    https://raw.githubusercontent.com/begin0808/Course_Scheduling_System/main/docker-compose.yml

# 3) 选择版本:编辑 .env
#    钉选版本(可控):IMAGE_TAG=v1.3.0
#    永远最新:        IMAGE_TAG=latest

# 4) 拉新映像并重启
docker compose pull
docker compose up -d
```

`docker compose up -d` 只会重建映像有变动的容器;`api` 一启动就自动跑迁移。完成后:

```bash
docker compose ps                 # 确认皆 healthy
curl http://localhost/api/health  # {"status":"ok"}
```

登录确认资料都在、版本正确:**左侧选单最下方**会显示「版本 v1.2.3」这样的版本号;系统管理员另可在「系统管理 → 系统版本」看到目前版本与最新正式版(v1.2.3 起)。

## 方式 B:从原始码建置部署

```bash
git pull                 # 取得新版原始码
docker compose up -d --build   # 重新建置并重启
```

## 关于版本钉选

- **正式环境建议 `IMAGE_TAG=v1.3.0` 这样钉住特定版本**,你才能决定何时升级、升到哪一版,而不是每次 `pull` 都可能变动。
- 想升级时,把 `IMAGE_TAG` 改成新版本号,再 `docker compose pull && up -d`。
- 各版本的变更内容见专案根目录的 [CHANGELOG.md](../../CHANGELOG.md);破坏性变更(若有)会在该版本明确标注 ⚠️ 与对应处置。

## 退回旧版(升级后发现问题)

因为资料与映像分离,换回旧版映像很单纯:

```bash
# .env 改回旧版本号,例如 IMAGE_TAG=v1.1.0
docker compose pull
docker compose up -d
```

> ⚠️ **注意资料库迁移方向**:若新版本引入了资料表结构变更,退回旧映像后其程序可能不认得新结构。**最保险的退回方式是:退回旧映像 + 还原「升级前那份备份」**(见[备份指南](backup.md)的还原流程)。若该次升级的 CHANGELOG 未标注 schema 变更,则单纯换映像即可。

### 从 v1.3.0 退回 v1.2.x

v1.3.0 改了资料表结构,**直接把版本号改回 v1.2.x,旧版会启动失败**(它不认得新的结构版本)。两种退回方式择一:

**方式一:用升级前自动备份还原(建议)**

1. 在 v1.3.0 的「系统管理 → 资料备份与还原」,选标示「升级前自动备份」的那一份按「还原」。
2. 还原完成后**立刻**把 `.env` 的 `IMAGE_TAG` 改回旧版本号,执行 `docker compose pull` 与 `docker compose up -d`。

资料会回到升级前那一刻;升级后才新增的资料(请假、调代课等)不会保留。

**方式二:退回指令(不需要备份,资料全部保留)**

还没开始使用单双周组时适用。在 `docker-compose.yml` 所在资料夹,**先以 v1.3.0 执行**:

```bash
docker compose run --rm --entrypoint alembic api downgrade 0017_class_name_unique
```

这会把资料表结构退回 v1.2.x 的样子(只移除单双周用的栏位),课表、请假、代课等资料都不动。
接著把 `.env` 的 `IMAGE_TAG` 改回旧版本号,执行 `docker compose pull` 与 `docker compose up -d`。

> 已经建了单双周组的话,旧版看不懂那些组的资料,请改用方式一。

## 升级检查清单

- [ ] 升级前已「立即备份」
- [ ] 已读该版本 CHANGELOG,确认有无 ⚠️ 破坏性变更
- [ ] **`docker-compose.yml` 已更新到新版**(容器组成可能有变动)
- [ ] `docker compose pull` 成功拉到新映像
- [ ] `docker compose up -d` 后六容器 healthy
- [ ] `/api/health` 回 ok,登录资料完整
- [ ] (如有 schema 变更)确认关键页面正常
